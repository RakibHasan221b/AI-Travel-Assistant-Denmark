| Trip Planner: 3 real bugs found via live testing | — | (1) Weather was only sometimes mentioned in the final answer — the Concierge's task never *required* it, just made it available as context. (2) Asking about one named place still got padded with irrelevant candidates and "not recommended" caveats. (3) `place_details`/`travel_time_estimate` used exact/substring name matching, which fails when the traveler's wording doesn't literally appear in the stored name (asked for "Little Mermaid statue", DB has the Danish "Den lille Havfrue" — zero text overlap) | done — `agent/crew.py` (explicit required-output instructions for both), `agent/tools.py` (`_resolve_place()`: falls back to semantic/pgvector search when exact matching finds nothing); verified live end-to-end with the exact failing query |
| Trip Planner: retry on malformed Groq tool calls | — | Groq/Llama occasionally emits a tool call that doesn't match the tool's schema (once as literal `<function=...>` tags instead of JSON, once as a JSON call missing required fields and sending `"limit": "5"` as a string instead of an integer) — Groq's strict parser rejects both outright, surfacing as `litellm.BadRequestError`. Not a rate-limit issue, so no cooldown needed | done — `agent/crew.py`'s `plan_trip()` catches `litellm.BadRequestError` with `tool_use_failed` in the message and retries once immediately; verified against the exact failing live query |
| Trip Planner: structured output instead of one paragraph | — | **The concept, explained for learning:** the Concierge used to write its whole answer as one free-text paragraph, which the Streamlit page just dumped on screen with `st.write()` — no cards, no distance/score shown visually, and no way to reliably parse it back into pieces. The fix has two halves that only work *together*: (1) the agent's output is now constrained to a real schema (`TripPlanOutput`/`PlaceRecommendation` pydantic models in `agent/crew.py`, via CrewAI's `Task(output_pydantic=...)`, backed by the `instructor` library) instead of asked for via a prompt instruction like "please respond in JSON" — a schema constraint is validated and retried automatically; a prompt instruction is just a hope. (2) `app/pages/2_Trip_Planner.py` then turns that structured dict into cards using plain Streamlit layout code (`st.container(border=True)`, `st.metric`, `st.caption`) — the exact same components the Explore page already uses, so the two pages look consistent. **Why this saves tokens, not costs more:** the "nice design" step is step (2) — ordinary Python running after the agent is already finished, zero additional LLM calls. Asking the LLM itself to "format nicely" would need *more* tokens per request and still just produce more text to parse, not real UI | done — `agent/crew.py` (`TripPlanOutput`), `api/main.py` (matching response model), `app/pages/2_Trip_Planner.py` (`render_trip_plan()`); verified two ways: a real live crew run producing valid structured JSON, and an offline `streamlit.testing.v1.AppTest` render of that real captured JSON with zero exceptions (no LLM call needed for this second check) |
| Trip Planner: result persists across reruns | — | Streamlit reruns the whole page script on every interaction (switching a dropdown, navigating to another page and back). The trip-plan result used to live in a local variable inside `if submitted:`, which Streamlit discards on the very next rerun — so switching anything, or leaving the page, made the result vanish | done — result now stored in `st.session_state.trip_plan_result`, which survives reruns and page navigation; only overwritten on a *successful* new request, so a failed retry doesn't wipe out a plan that already worked |
| Trip Planner: 2 more real bugs found via live testing, same day | — | (1) A compound request ("see X **and** get coffee nearby" — a named place plus an open-ended part) was silently collapsed to just the named place: the earlier "don't pad single-place requests" instruction didn't explicitly cover the case where a request has *both* a named place and an open-ended part, so the LLM sometimes guessed wrong and dropped the open-ended half entirely. (2) `search_places`/`top_quality_places`'s `limit` tool argument is typed `int`, but Groq/Llama sometimes generates it as a JSON string (`"3"` instead of `3`) — Groq's own server-side schema validation rejects the whole tool call outright when that happens, *before* our code ever runs, so the earlier retry-once fix wasn't reliable against this specific failure (it can fail the same way twice in a row) | done — `agent/crew.py`'s scout/concierge tasks now explicitly enumerate both request parts and require covering each one; `agent/tools.py` adds `_coerce_limit()` and widens `limit`'s declared type to `int \| str` so Groq's schema validation accepts what the model actually tends to send, then coerces it locally. Also made `overall_note` a required 2-4 sentence narrative tying the recommendation together (previously optional and usually left blank) — addresses separate feedback that the old free-text paragraph "felt like a nicer report" than cards alone; now both. Verified live end-to-end with the exact failing query: returned the landmark + 3 real cafes, no tool errors, real narrative note |
| Trip Planner: real geographic "near X" search | — | "Coffee near the Little Mermaid" was never actually checked for proximity — `search_places` only does semantic/text similarity, and the distance shown on cards was measured from the *traveler's own starting point*, not from the landmark. A cafe could rank highly purely because its description happened to use similar wording, while being genuinely far from the place it was supposed to be near | done — new `search_places_near(anchor_place, category, limit)` tool (`agent/tools.py`): resolves the anchor place's real coordinates, then ranks candidates by actual haversine distance (reusing the same math as `travel_time_estimate`), not text similarity. Verified directly against the live DB: real cafes 0.3-0.7 km from the statue, vs. the old semantic-search results which were 5-6 km away. `PlaceRecommendation` gained `near_place`/`near_distance_km` fields (distinct from `distance_km`, which stays "from your starting point") plus `opening_hours`, which the structured schema had dropped entirely versus the old free-text version. Chaining this across multiple stops (A → near A finds B → near B finds C) is a real, larger extension, deliberately not built yet — noted as a next step, not squeezed in |
| Trip Planner: result caching to cut real Groq token usage | — | Building and testing today's Trip Planner fixes burned through Groq's actual free-tier daily token cap (100,000 TPD) from repeated live crew runs — a real, felt problem, not hypothetical. Re-submitting the same question, or the same question from a different starting point, was re-running all 3 agents from scratch every time | done — new `trip_plan_cache` table (`db/schema.sql`) plus caching logic in `agent/crew.py`'s `plan_trip()`, checked before any LLM call: (1) an exact repeat (same request+date+start_location, within a 24h TTL) returns the saved result instantly, zero tokens; (2) the same request+date with a *different* start_location reuses the cached places/weather/summary (they don't depend on where the traveler starts) and only recalculates the travel-time fields with plain haversine math — also zero tokens. That math was extracted into a shared `travel_fields()` function in `agent/tools.py` so the live `travel_time_estimate` tool and the cache's recompute path can't drift apart into two different formulas. Verified end-to-end with a seeded cache row and zero Groq calls: exact-match lookup, same-request-different-location lookup, and the recomputed distance for a new location (3.95 km for Nørrebro vs. 6.8 km for Vanlose, both correct) all confirmed working; covered by `tests/test_crew.py` |
| Trip Planner: fixing a real rate-limit crash, root cause not symptom | — | A live run failed with `litellm.RateLimitError`. Instrumenting a real crew run with litellm's own usage callback (logging every LLM call's exact token count, not guessing) found the actual cause: the Place Scout was calling the same two tools with identical arguments 5 times in a row, never recognizing it already had its answer — each repeat resent the whole growing conversation, burning ~12,000 tokens on a task that needed one round of tool calls. A follow-up test of `openai/gpt-oss-120b` for its larger daily quota (200K vs 100K TPD) was rejected on real evidence: its lower 8,000 TPM ceiling made a single run *more* likely to fail than the current model's 12,000 TPM, since one request's calls all land in the same short burst — daily headroom doesn't help if a single request can't finish | done — (1) explicit stop-once-you-have-results instruction added to every agent task, confirmed live: Scout dropped from 5+ calls (~12,000 tokens) to 2 calls (~3,900 tokens); (2) `place_details`/`travel_time_estimate` batched to accept comma-separated place lists instead of one call per place; (3) default "nearby" candidate count cut from 5 to 3; (4) `plan_trip()`'s automatic retry removed entirely — a retry re-runs the whole crew, not just the failed call, so on a 100,000/day budget an automatic retry was gambling a full run's tokens on a coin-flip, and losing that gamble on 2 retries could burn ~27,000-37,000 tokens from a single click; (5) the Conditions Analyst agent folded into the Concierge as one more tool call — its whole job was "call weather_conditions once, summarize it," and every separate CrewAI agent hands off pays a real fixed cost (its own backstory + task description + opening LLM call) before doing any work, measured live at ~1,400-1,600 tokens per run for a task that small. Covered by `tests/test_crew.py`, `tests/test_agent_tools.py` |
